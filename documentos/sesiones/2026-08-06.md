## Lo que se hizo

### Sistema de retiros para repartidores (base, sin Stripe Connect todavía)

Antes de construir nada se investigaron las fórmulas existentes de "cuánto gana un repartidor por pedido" y se encontraron **tres inconsistentes convivendo en el código**: `rider_stats.dinero` (acumulaba el 100% del pedido, incluyendo lo del restaurante — mal), un cálculo del 15% que solo se usaba en un texto de notificación push (nunca se guardaba), y el que ya usa el panel de Flota (`SUM(delivery_fee)`, correcto). Se confirmó con el patrón que la fórmula correcta es esta última, y que **solo los `repartidor_plus` independientes** entran en este sistema — los de flota los paga su jefe de flota fuera de la plataforma.

- Tablas nuevas: `rider_withdrawals`, `rider_payout_accounts` (CLABE + columnas `stripe_*` reservadas para el futuro), `withdrawal_status_log`. Estado como TEXT libre (no ENUM) para poder agregar estados nuevos sin migración.
- Saldo **siempre calculado en vivo** (nunca guardado) vía `get_rider_balance()`, justo para no repetir el bug de `rider_stats.dinero`.
- `request_withdrawal()` y `admin_transition_withdrawal()` como funciones `SECURITY DEFINER` que validan y hacen la transición de estado de forma atómica; un índice único parcial (`one_open_withdrawal_per_rider`) es la verdadera protección contra dos solicitudes simultáneas, no una validación de aplicación.
- **Bug de seguridad real encontrado y corregido**: `is_admin()` regresaba `NULL` (no `false`) cuando no había sesión, y `IF NOT is_admin()` en PL/pgSQL trata `NULL` como "no bloquear" — un llamado sin autenticar casi lograba pasar la verificación de administrador. Se confirmó el hueco con pruebas `curl` directas y se corrigió envolviendo todo en `COALESCE(..., false)`.
- Capas Dart nuevas siguiendo la misma convención del proyecto: `models/rider_withdrawal.dart` (+ `rider_balance.dart`, `withdrawal_status.dart`) → `repositories/rider_withdrawal_repository.dart` → `services/rider_withdrawal_service.dart` → `controllers/rider_withdrawal_controller.dart` (registrado en el `MultiProvider` de `main.dart`).
- Se reescribió `_showRetiros()` en `repartidor_plus_screen.dart` (que ya existía visualmente pero era 100% falso: saldo mal calculado, botón "Solicitar retiro" que no hacía nada, historial inventado) para que use el sistema real, con un diálogo nuevo para pedir el monto.
- Panel de Admin nuevo: `admin_retiros_screen.dart` (Lista/Estadísticas, búsqueda, filtros, detalle con acciones Aprobar/Rechazar/Completar/Cancelar), ruta `/admin/retiros`, entrada en el menú "Más" con contador de pendientes.
- Se extendió la Edge Function `admin-user-lookup` (de la sesión de Reseñas) para regresar también foto y nombre del repartidor.

Se agregó `_truncateTitle()` en `restaurants_screen.dart` para el título (con `maxLines`/`overflow` como respaldo); la descripción ya tenía el recorte correcto.

### Límites de caracteres visibles al crear un platillo (panel del dueño)

El patrón preguntó si al crear un platillo se ven los límites de caracteres — no se veían. ### Filtro de categorías — tres vueltas hasta encontrar lo que pedía el patrón

Petición relayada con un dibujo a mano (rotado, difícil de leer): "es un filtro y debe haber categorías". Se armó en tres intentos, cada uno corregido con la siguiente pista real:

1. Primer intento: filtro multi-selección **dentro** del menú de un restaurante (interpretación inicial, confirmada por el usuario en ese momento). Se construyó y funcionó, pero el patrón avisó "no aparece el filtro" — una captura nueva con flecha dibujada mostró que en realidad lo quería en la **lista principal de restaurantes**, entre el buscador y las tarjetas.
2. Segundo intento: fila de chips siempre visible en la lista principal, alimentada por las categorías de MENÚ de cada restaurante (lo que cada dueño escribió para organizar sus propios platillos). El patrón corrigió: debía ser un botón con fondo blanco que al tocarlo abre las categorías (no una fila siempre visible) — se cambió a un botón "Categorías" + contador que abre una hoja inferior, y se agregó una segunda variante experimental (para comparar) que despliega hacia el lado, igual que el buscador.
3. **Corrección de fondo**: el patrón aclaró que su jefe pidió que la categoría se elija **al registrar el restaurante** (Comida rápida, Bebidas, Postres...) de una lista fija — "no se mete imaginación" — y que ESA es la que debe alimentar el filtro del cliente, no las categorías de menú de cada uno.

Se implementó la arquitectura correcta:
- `lib/core/restaurant_categories.dart` → `kRestaurantCategories` (lista fija: Comida rápida, Bebidas, Postres, Antojitos mexicanos, Mariscos, Pizza, Comida asiática — solo las primeras 3 las pidió el patrón directamente, el resto se agregaron como default razonable a confirmar).
- Columna nueva `restaurants.categorias TEXT[]`, campo `categorias` en el modelo `Restaurant`, selector de chips en `registro_restaurante_screen.dart` (alta) y en `dueno_screen.dart` (edición, sección "Categoría de tu restaurante").
- El filtro en `restaurants_screen.dart` (ambas variantes, botón+hoja y el despliegue lateral) ahora lee directo de `Restaurant.categorias`.
- Se le asignó categoría real a los 15 restaurantes existentes en Supabase (ej. McDonalds → Comida rápida, Starbucks → Bebidas, Sushi Roll → Comida asiática, etc.) para que el filtro no apareciera vacío.
- Limpieza en el mismo movimiento: se quitó el método `getAllRestaurantCategoryNames()` y el estado que quedaron sin uso al cambiar de fuente de datos.

### Categorías de menú — de nombres específicos a una lista genérica

Ya con el filtro de restaurante resuelto, el patrón pidió también generalizar las categorías de MENÚ (las pestañas dentro de cada restaurante, ej. "Hamburguesas" no generaliza bien si también venden hot dogs o tortas). Se investigó primero y se confirmó que **no existe ninguna UI en la app para crear/editar categorías de menú** — se insertan siempre por SQL directo — así que el arreglo fue sobre todo de datos y de criterio a futuro, no de pantallas nuevas.

- Se armó una lista fija de 7 categorías genéricas: Platillos, Entradas, Ensaladas, Desayunos, Acompañamientos, Postres, Bebidas (`lib/core/product_categories.dart` → `kProductCategories`).
- Primero se decidió NO migrar los restaurantes existentes (dejarlos como estaban) — pero el patrón cambió de opinión después y pidió aplicarla también a los 15 restaurantes ya existentes.
- Se migraron las ~40 categorías reales: renombrados simples (ej. "Hamburguesas"→"Platillos", "Papas"→"Acompañamientos") y 4 fusiones donde varias categorías específicas de un mismo restaurante caían en la misma genérica — reasignando primero los platillos a la categoría que sobrevive y luego borrando la fila redundante, para no perder ningún platillo:
  - CarnitasElPuerco: "Antojitos"+"Carnitas por Kilo"+"Tacos" → "Platillos"
  - TacosChuy: "Quesadillas"+"Tacos" → "Platillos"
  - Starbucks: "Cafés"+"Frappes" → "Bebidas"
  - Nieves Tepa: "Nieves"+"Paletas" → "Postres"
- Se verificó con una consulta a Supabase que 0 platillos quedaron sin categoría o con una categoría inválida tras la migración.

### Pestañas de categoría dentro del restaurante — de vuelta a selección única

El patrón mandó una captura señalando las pestañas "Hamburguesas / Papas / Bebidas" del menú de McDonalds, todas marcadas con check al mismo tiempo — aclaró que ahí solo se debe poder elegir una a la vez (esa selección múltiple se había dejado del primer intento del filtro, cuando todavía se pensaba que iba dentro del restaurante). Se revirtió el `onSelect` de `_CategoryTabsRow` en `restaurants_screen.dart` para que cada toque reemplace la selección en vez de sumarla.

### McDonalds marcado como Premium

De paso en la misma captura, el patrón indicó que esa cuenta de prueba (McDonalds) debía ser Premium. Se activó por SQL directo (`is_premium = true`), como ya es la práctica para este plan (sin UI de cobro todavía).

### Bug de metadatos `.webp` en la subida de imágenes (web)

Pregunta del patrón sobre si las imágenes subidas en `.webp` se manejan bien. Se confirmó que en celular todo se comprime y convierte a `.webp` sin importar el formato de origen (correcto). Pero se encontró un bug real en la rama web de `uploadProductImageBytes`/`uploadProfilePhotoBytes`: el archivo se subía siempre etiquetado como `.jpg`/`image/jpeg` sin revisar el formato real de los bytes. Se corrigió agregando `_detectImageExt()` (detecta el formato real por sus bytes mágicos: WEBP/PNG/JPG/GIF) y `_mimeForExt()`, usados ahora en la rama web de ambas funciones.
