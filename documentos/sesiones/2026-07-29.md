# Sesión 2026-07-29 — Miércoles

## Resumen del día

Se corrigió una brecha de seguridad real (el código de Admin estaba filtrado dentro del binario de GOGO Food, además de existir en su app separada), y se separó **GOGO Flota** en su propia app — mismo patrón que Admin: entry point Dart propio, flavor de iOS propio, APK de Android propio y sitio web propio. Después, en la misma sesión, se le dio un ícono propio a Flota, se resolvieron 6 pendientes de la app (visibilidad de ganancias para riders de flota, banners del dueño, seguridad del perfil, nombre de usuario, promos expiradas), y se implementó OXXO Pay de verdad (antes era solo un botón decorativo) — incluyendo desplegar Edge Functions y configurar el webhook de Stripe.

## Lo que se hizo

### Hallazgo: Admin estaba duplicado dentro del router del cliente
- `lib/router.dart` (usado por `main.dart`, la app cliente) todavía tenía registradas `/admin` y `/admin-login`, con `AdminScreen`/`AdminLoginScreen` importadas — a pesar de que `main_admin.dart` ya existía como app separada
- Esto significaba que el código de Admin **sí se compilaba dentro del APK/IPA de GOGO Food**, aunque estuviera gateado por un `redirect` en tiempo de ejecución (no es una barrera de seguridad real, solo evita la navegación normal)
- Se quitó `/admin` y `/admin-login` de `router.dart` — Admin ahora vive exclusivamente en su propio binario

### GOGO Flota — separada en su propia app
- **Antes:** `/flota-login` y `/flota` vivían dentro del router compartido del cliente, igual que tenía Admin (mismo problema)
- **Ahora:** `lib/main_flota.dart` nuevo — entry point Dart propio, su propio `GoRouter` (solo `/flota-login` y `/flota`), sin nada del cliente
- Se quitaron esas rutas y sus imports de `router.dart`, y se limpiaron las referencias a `admin`/`jefe_flota` en `_roleHome()`, el bloqueo de rutas por rol, `splash_screen.dart`, `login_screen.dart` y `auth_service.dart` (todas apuntaban a `/admin` o `/flota`, rutas que ya no existen en ese router)

### iOS — flavor "flota" (mismo patrón que Admin)
- Nuevo flavor en Xcode: `Debug-flota` / `Release-flota` / `Profile-flota`, bundle id `com.fercadi.flota`
- Archivos nuevos: `ios/Runner/Info-Flota.plist` (nombre "GOGO Flota", esquema `fercadiflota://`), `ios/Flutter/*-flota.xcconfig`, scheme `flota.xcscheme`
- `ios/Podfile` — mapeo de las 3 configs de flota agregado
- Se usó el gem `xcodeproj` (Ruby) para clonar las configuraciones de "-admin" a "-flota" en los 4 targets del proyecto (Runner, RunnerTests, GOGOTrackingWidgetExtension, y a nivel de proyecto), con respaldo de `project.pbxproj` antes de tocar nada

### Bug encontrado y corregido: bundle id del widget mal prefijado
- Al compilar el flavor de flota apareció: *"Embedded binary's bundle identifier is not prefixed with the parent app's bundle identifier"*
- Causa: el widget de pantalla de inicio (`GOGOTrackingWidgetExtension`) tenía el bundle id fijo `com.fercadi.app.GOGOTrackingWidget` en **todas** las configuraciones, incluyendo las de Admin y Flota — pero un binario embebido necesita estar prefijado por el bundle id de la app que lo contiene
- Este bug ya existía para Admin (nunca se había notado porque nadie había compilado esa combinación hasta ahora)
- **Fix:** `com.fercadi.admin.GOGOTrackingWidget` para las configs de admin, `com.fercadi.flota.GOGOTrackingWidget` para las de flota
- Se verificó compilando los tres flavors (`flutter build ios --no-codesign` para cliente, admin y flota) — los tres compilan limpio

### Web — GOGO Flota también necesita su propio sitio
- El jefe de flota usaba el panel desde `web-iota-brown-32.vercel.app/flota-login` (el mismo sitio del cliente) — al sacar esas rutas del router del cliente, ese acceso se hubiera roto
- Se decidió (con el usuario) darle también su propio sitio web: `flutter build web --target lib/main_flota.dart` a una carpeta de salida separada (`build/web-flota`)
- Esto además resuelve de raíz un problema viejo documentado (sesión de Supabase del jefe de flota interfiriendo con la sesión del cliente en el mismo navegador) — al ser otro dominio, ya no comparten `localStorage`
- **Pendiente:** desplegar `build/web-flota` a un proyecto de Vercel separado — no se hizo desde esta Mac porque la cuenta de Vercel logueada aquí no es la correcta (mismo problema ya documentado el día anterior); se deja para cuando se use la cuenta correcta

### `build_apks.ps1`
- Se agregó una tercera invocación para generar `GOGOFlota.apk` (`FLUTTER_APP_ID = com.fercadi.flota`, `--target lib/main_flota.dart`)

## 6 pendientes de la app resueltos

### 1. Repartidor de flota ya no ve "Ganancias hoy / Entregas"
- La pantalla real del repartidor es `repartidor_screen.dart` (ruta `/repartidor`), no `repartidor_plus_screen.dart` como se pensó al principio
- Nueva función `SupabaseService.riderTieneFlota()` — consulta `flota_members` por `rider_id` del usuario actual
- Si pertenece a una flota, se oculta la tarjeta de estadísticas — esas cifras las administra su jefe de flota desde su propio panel

### 2. Banner del dueño: un solo campo de descuento
- Antes había que escribir el badge visual ("35%") Y el número real del descuento ("35") por separado, en dos campos distintos
- Ahora, cuando hay un producto vinculado, solo se pide el número una vez y el badge (`-35%`) se genera solo
- El campo de texto libre para el badge sigue existiendo únicamente para banners sin producto vinculado (ej. "NUEVO")

### 3. Formulario de "tarjeta de banco" eliminado del perfil
- Se confirmó que era 100% decorativo: guardaba el número de tarjeta completo en texto plano en SharedPreferences (`auth_service.dart` → `getCard`/`saveCard`/`clearCard`), nunca se conectaba a Stripe
- El pago real con tarjeta en checkout siempre usó el SDK de Stripe (PaymentSheet) desde cero, sin tocar esos datos guardados
- Riesgo de seguridad real sin ningún beneficio funcional — se quitó por completo (formulario, funciones, controllers)

### 4. Nombre de usuario que cambiaba solo
- Causa: `splash_screen.dart` nunca sincronizaba `session_email` al restaurar una sesión ya existente de Supabase, así que a veces el nombre se leía con la clave equivocada (`guest:...` en vez de `<email>:...`) y mostraba "Usuario" por defecto
- Fix: sincronizar la sesión local también en ese camino, no solo al hacer login explícito

### 5. Promo expirada ya no se borra al editar el platillo
- En `dueno_screen.dart`, si el dueño editaba un platillo (por cualquier motivo) después de que su promo expirara, el descuento configurado se borraba solo al guardar — porque el modo "Promo" se inicializaba apagado para promos vencidas, y el guardado escribía `null` en esos campos
- Fix: si el dueño no toca la sección de promo en esa edición, se conserva tal cual lo que ya había, activo o no — así se puede reactivar después sin volver a configurarlo desde cero

### 6. OXXO Pay implementado de verdad
Antes era un alias visual de "Efectivo": seleccionarlo no generaba ninguna ficha real, el pedido se creaba igual que con efectivo.

- **Edge Function `create-payment-intent`** actualizada: acepta `paymentMethodType`, y cuando es `"oxxo"` crea el PaymentIntent con `payment_method_types: ['oxxo']` en vez de `automatic_payment_methods`
- **`checkout_screen.dart`**: nueva función `_payWithOxxo()` que confirma el pago con `Stripe.instance.confirmPayment(...)` y `PaymentMethodParams.oxxo(...)`, muestra la ficha real (referencia + botón para abrir/imprimir) en un diálogo, y solo entonces crea el pedido con `payment_status: 'pending'`
- **Nueva Edge Function `stripe-webhook`**: verifica la firma de Stripe manualmente (HMAC-SHA256 con Web Crypto, sin necesitar el SDK completo de Stripe) y marca el pedido como `payment_status: 'paid'` cuando Stripe confirma que el cliente ya pagó en la tienda OXXO — esto es asíncrono, puede tardar horas/días
- **Nuevas columnas en Supabase**: `orders.payment_status` y `orders.stripe_payment_intent_id` (SQL corrido por el usuario en el SQL Editor de Supabase)
- **Configuración externa completada en esta sesión** (con el usuario siguiendo instrucciones paso a paso en su Dashboard de Stripe, en español):
  1. OXXO habilitado en Stripe (Configuración → Métodos de pago)
  2. Se instaló el CLI de Supabase en esta Mac (`brew install supabase/tap/supabase`) y se autenticó con un Personal Access Token generado por el usuario (`sbp_...`, usado solo en la sesión, no guardado en el repo)
  3. Proyecto vinculado (`supabase link --project-ref mmjzyqvjdwhzefbaiums`) y ambas funciones desplegadas (`supabase functions deploy create-payment-intent`, `supabase functions deploy stripe-webhook --no-verify-jwt`)
  4. Webhook creado en el Dashboard de Stripe apuntando a `https://mmjzyqvjdwhzefbaiums.supabase.co/functions/v1/stripe-webhook`, escuchando `payment_intent.succeeded` / `.payment_failed` / `.canceled`
  5. `STRIPE_WEBHOOK_SECRET` (obtenido del webhook recién creado) guardado en Supabase vía `supabase secrets set`

### Problema encontrado al probar OXXO en el iPhone (sin resolver al cierre de la sesión)
- Al probar el pago con OXXO en el iPhone de angelo, Stripe rechazó la confirmación con `POST /v1/payment_intents/.../confirm` → **400** (visible en el log de `flutter run --debug`, pero sin el mensaje detallado del error todavía)
