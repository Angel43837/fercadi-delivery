# Sesión 2026-08-04 — Martes

## Resumen del día

Se implementó de punta a punta el plan **GOGO Premium** para el panel de Dueño, pedido directamente por el negocio: banners bloqueados en el plan gratis, tope de 7 platillos (20 en Premium), y — agregado ya avanzada la sesión — promociones por platillo también bloqueadas en el plan gratis. En el camino se encontró y corrigió un bug real de cómo se vincula una cuenta de dueño a su restaurante, que había hecho que la primera cuenta de prueba mostrara el restaurante equivocado.

## Lo que se hizo

### GOGO Premium — planteamiento
Pedido del negocio (relayado): banners, y un tope de platillos de 7 en el plan gratis contra ~20 en Premium, con una cuenta de prueba nueva para probar ambos estados.

- Columna nueva `restaurants.is_premium BOOLEAN NOT NULL DEFAULT false` (Supabase Management API)
- Cuenta de prueba nueva `dueno.prueba@fercadi.com` / `Prueba2026!`, pensada para probar el plan **gratis**
- `dueno_screen.dart`: estado `_isPremium`, constantes `_maxProductosGratis = 7` / `_maxProductosPremium = 20`, fetch de `is_premium` en `_initRestaurant()` vía nueva `SupabaseService.getRestaurantIsPremium()`
- Widget `_buildPremiumLocked(...)` — tarjeta de "candado" reutilizable (ícono, título, descripción, badge "Disponible con GOGO Premium")
- `_buildBanners()` ahora regresa `_buildPremiumLocked(...)` en vez de los banners reales cuando `!_isPremium`

### Tope de platillos (7 / 20)
- El botón "Nuevo platillo" ahora revisa `_products.length >= _maxProductos` antes de abrir el formulario de creación
- Si se llegó al tope, muestra un diálogo (`_showLimiteProductosDialog`) explicando el límite en vez de abrir el formulario — no afecta editar platillos que ya existen, solo bloquea crear nuevos

### Bug encontrado: la cuenta de prueba mostraba el restaurante equivocado
- Al asignar el restaurante "Pollo Feliz" (ya existente, sin dueño) a la cuenta nueva, se hizo vía `UPDATE restaurants SET owner_id = ...` — pensando que así quedaba vinculada
- Pero el panel de dueño **no usa `owner_id`** para decidir qué restaurante mostrar — usa `user_metadata.restaurant_id` (`AuthService.getRestaurantId()`), que si no está seteado cae al restaurante por defecto (`'1'`, el mismo que ya usaba otra cuenta de prueba existente) — de ahí que el negocio reportara "es el mismo restaurante que ya tenía"
- Se confirmó con `grep` que `owner_id` es prácticamente de solo-escritura en todo el código: solo se escribe al auto-registrarse un restaurante nuevo (`registro_restaurante_screen.dart`), nunca se lee en ningún otro lado
- **Fix real:** login con la cuenta de prueba (password grant vía API de Supabase) + `PUT /auth/v1/user` para setear `user_metadata.restaurant_id = 'r_pollo'` directamente
- Documentado en `manual_backend.md`, `GOGO_FOOD_DOCUMENTACION_COMPLETA.md` (P5) y `CLAUDE.md` para que no se repita el mismo error

### Promociones por platillo también bloqueadas en el plan gratis

- El editor de un platillo tiene un toggle "Normal / Promo" que activa descuento o 2x1 para ese producto — se bloqueó igual que los banners
- Si `!_isPremium`, la pestaña "Promo" muestra un candadito y, al tocarla, abre un diálogo (`_showPromoLockedDialog`) en vez de activar el modo promo

### Segunda cuenta de prueba — para ver el lado Premium
- El negocio pidió dejar la otra cuenta de dueño que ya tenía (restaurante **TacosChuy**) tal cual, para poder comparar los dos planes lado a lado
- Se activó `is_premium = true` directamente en `TacosChuy` por SQL (Management API), sin tocar Pollo Feliz — así `dueno.prueba@fercadi.com` (Pollo Feliz) queda como ejemplo del plan gratis y la cuenta de TacosChuy como ejemplo de Premium con todo desbloqueado
